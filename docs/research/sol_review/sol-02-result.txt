## 1. EXECUTIVE FINDING

**Yes. The supplied TANUQ source exposes authority failures that the LUNA conclusions did not identify.** An agent able to invoke the same local CLI used for the generic agent integration can grant its own HIGH/CRITICAL approval. It can also use `tanuq export --out` to write an arbitrary filesystem path without scope or approval checks, and `tanuq init --force --yes` to replace a narrower workspace scope with the whole workspace. These are TANUQ command paths, not merely hypothetical calls to a low-level writer.

That conclusion has a prerequisite: **the agent must be able to invoke CLI commands, not only submit proposal JSON to a restricted hook.** The packet documents CLI-driven agent integration but does not establish that every deployment gives every model shell access. For a genuinely JSON-only proposer, the supplied source does not establish these CLI attack paths.

There is also an unauthenticated local HTTP read of pending proposal content. A separate, potentially more consequential route—execution of agent-written code by TANUQ’s verifier—needs one targeted experiment before it can be called confirmed.

## 3. MUTATION ENTRY-POINT MAP

The **governed product file-change path** is CLI `propose`/`execute`, web `/api/propose`/`/api/execute`, or Claude `handle_pretooluse` → `OperationCoordinator.execute` → `agent_adapter.execute` → the runtime’s `WorkerActionPipeline`. Claude’s handler always returns tool `deny` after delegating; it does not apply the Edit or Write itself.

Not every meaningful mutation in the supplied product source converges there:

- **Approval-state mutation:** `cli.py` `cmd_approve` and `web.py` `_approve` delegate to `agent_adapter.approve` → `ApprovalStore.grant`. They do not run an apply pipeline; this is properly a separate authority boundary, but the CLI boundary has no human-authentication check.
- **Authoritative scope mutation:** `cli.py` `cmd_init` → `config.py` `init_workspace`/`save_config` writes config directly. `--force` permits re-registration.
- **Arbitrary output-file mutation:** `cli.py` `cmd_export` uses `Path(args.out).write_text(payload)` after producing a read-only *bundle*. Its output write has no governed-path constraint.
- **Integration/configuration mutation:** `web.py` `_install_claude` writes `.claude/settings.json` directly behind a token-protected POST. `cmd_token`, workspace registry pruning, and runtime dummy-test creation also write TANUQ-owned state, not proposed source patches.
- **Lowest-level file primitive:** `tests/test_p3_adversarial_proposals.py::test_p3_no_direct_write_bypass_around_pipeline` actually asserts that `FileApplier.apply(high, scope=(...))` writes a HIGH patch without approval. That is an explicitly demonstrated **direct primitive**, not evidence that an agent restricted to proposal JSON can reach it.

Recovery and session-bridge tests show delegation into supplied pipelines; external-action tests exercise a **different** `ExternalActionPipeline`, journal, and provider boundary. `tanuq/runtime.py` does not assemble that external pipeline. Replay tests reconstruct state, not source-file mutations. The `agent_run.py` tests establish an additional CLI exists, but its implementation is not in this packet; its production configuration cannot be inferred from test names.

## 4. APPROVAL / REPLAY / CONCURRENCY

`agent_adapter.approve` reconstructs a pending patch, reevaluates governance, compares any stored fingerprint to the recomputed fingerprint, and grants against fingerprint/path/action/current risk at `attempt=1`. `agent_adapter.execute` reconstructs pending patches and sends them through the pipeline. The approval tests provide substantive evidence for wrong-fingerprint/path/action/risk/attempt denial, consume-once behavior, expiry **when an expiry is supplied**, and durable consumption after restart. The anchored-ledger tests also explicitly demonstrate a remaining historical limitation: a consistent rewind of both ledger and keyed anchor to a previously anchored state can revive a grant.

Two qualifications matter:

1. **Consumption is not authentication of the grantor.** A perfectly bound, single-use approval is still self-issued if the agent calls `cmd_approve`.
2. `OperationCoordinator`’s in-flight dictionary is **per coordinator object**. `web.py` `_execute` constructs a new `OperationCoordinator(SERVICE.env)` for each request, and CLI invocations are separate processes. Different selector keys (`NEXT`, `ALL`, `fp:…`) also need not identify different pending patches. LUNA-07’s claim of a general same-proposal concurrency reservation does not follow from this source. Ledger consumption tests mitigate approval replay; the supplied tests do not prove atomicity of every file check–write–verify interleaving.

**TTL remains unresolved for the product grant:** `agent_adapter.approve` advertises `APPROVAL_TTL_SECONDS` but does **not** pass `expires_at` to `ApprovalStore.grant`. The store’s default expiry behavior is not printed in the packet. Tests of explicitly supplied expiry do not settle this call site.

## 5. GOVERNANCE-INPUT ANALYSIS

`agent_adapter._validate_item` keeps only path, action, reason, old content, and new content. `_propose_one` supplies `env.config.allowed_paths`; `propose` recreates accepted patches with those paths. Claimed approval, verification, risk, confidence, policy, and externally supplied `allowed_paths` do not become authoritative through that JSON interface. `pending.patch_from_record` does read stored `allowed_paths`, but the product pipeline also receives configured scope; tests specifically deny a proposal’s attempt to expand that scope.

The tests support reason-invariant deterministic classification, not semantic safety of every possible diff. Research E1/E3 records report LOW/MEDIUM accepted changes with dangerous composed meaning; those are bounded risk/observation findings, not proof that a forged governance field reached `RiskPolicy`. Conversely, a CLI caller’s ability to call `approve` or `init --force` is **not** a proposal-field manipulation: it crosses from proposer to operator-command authority.

## 6. SCOPE / POLICY / TOCTOU

`validate_config_values` rejects configured paths outside the resolved workspace; static out-of-scope, traversal, and symlink-read tests establish useful boundaries for their tested cases. It does not enforce *monotonic narrowing relative to the previous configuration*: `cmd_init --force --yes` defaults allowed paths to the workspace and `save_config` replaces the earlier config. A newly loaded pipeline then takes that wider scope.

Stale `old_content` is checked in pipeline tests, and apply-failure tests show no verification after a failed write. They do not establish a filesystem transaction spanning validation, approval, final path resolution, file replacement, and verification. The core `PathPolicy`/`FileApplier` implementations are not printed here; a symlink-swap or concurrent replacement exploit must not be asserted from static-symlink tests alone. Approval records bind a risk context, not a demonstrated policy-version/content hash; the supplied policy-change tests exercise an upgrade that changes the risk level, not every same-level policy change.

## 7. APPLY / VERIFICATION

For the governed product call, `agent_adapter.execute` supplies `[str(env.workspace)]` as verify paths and `select_test_targets` as test targets. `verification_profile.related_test_candidates` selects existing related tests inside the **workspace**; `select_test_targets` excludes a same-run patch target by resolved path and otherwise falls back to `env.ensure_dummy_test()`. It does not require selected tests to lie inside the configured `allowed_paths`, and path exclusion does not establish that a test will not **import** the newly patched application module.

Tests show that verification failure triggers rollback in exercised cases; a passing selected test is not a proof that the bytes verified remained unchanged afterward, that the test did not perform other writes, or that semantic behavior is safe. TANUQ explicitly states there is no OS sandbox. Whether a real selected pytest target can turn an auto-approved application-code proposal into an out-of-scope side effect during verification is therefore a material **unexecuted** attack-path question, not a confirmed result of the supplied tests.

## 8. EVIDENCE / RECONCILIATION

The runtime wires keyed event and approval-ledger anchors and a separate apply journal. Tests show event-chain integrity, ledger reload/single use, and journal state/hash checks in the cases exercised. They do **not** make a keyed chain proof of who invoked `cmd_approve`, nor make an apply journal’s expected content hash a measurement of all filesystem effects.

`cmd_verify` reports event chain/anchor and approval-ledger validity; it does not itself compare governed disk bytes to journal hashes. `incidents.collect_incidents` detects specified journal/recovery anomalies but does not scan for ordinary post-verification drift. `reconciliation.reconcile_workspace` does that comparison **on demand** for journal/pending paths only; its own JSONL parser does not validate the journal hash chain. Its `MATCH` is a point-in-time observation, not prevention, and ungoverned files have no baseline there. The E5 research predating the shipped command must not be read as saying reconciliation is still research-only: `cli.py` registers it and `tests/e5_reconciliation_test.py` executes a real CLI apply → out-of-channel edit → `CONTENT_MISMATCH`.

There is also a projection limitation: `evidence.lineage` groups by fingerprint and retains one `execution`. A repeated, identical fingerprint with a later validation denial can still be presented by `operations` as the earlier `VERIFIED` execution. The underlying events remain available; this is **OBSERVABILITY ONLY**, not proof of forged durable records.

## 9. PREVIOUS LUNA FINDINGS

- **LUNA-07:** Fingerprint/context, consumption, and restart tests support substantial approval binding. The record overstates the coordinator’s concurrency reservation: it is instance-local, and web creates a fresh instance per execute. Binding also says nothing about authenticating the person who grants.
- **LUNA-08/09:** The supplied tests do not show approved patch bytes being substituted inside `FileApplier`; an applied-content fingerprint is not established as a missing authorization check. But reconciliation cannot account for an unjournaled write by `cmd_export` or a possible verifier side effect. “No applied-content-fingerprint blocker” is narrower than “no new authority gap.”
- **LUNA-10:** The JSON proposal’s claimed governance fields do not become authority in the shown TANUQ adapter. The conclusion misses agent access to **operator commands**, which changes authoritative approval/config state rather than merely influencing a risk input.
- **LUNA-11:** `load_environment` explicitly wires governance and scope for TANUQ’s product pipeline. This does not prove every source-file mutation exposed by TANUQ passes that pipeline: `cmd_export --out` plainly does not. Tests showing a risk-disabled recovery assembly do not, by themselves, prove that `agent_run.py` ships with that configuration.
- **LUNA-12:** Recovery/bridge/external tests support their tested delegation paths. They do not cover the product CLI’s export output write, force re-initialization, or unauthenticated GET of pending content.

## 10. NEW FINDINGS

**CONFIRMED SECURITY GAP — CLI self-approval and false human attribution.**  
**Files/symbols:** `tanuq/cli.py` `cmd_approve`; `tanuq/agent_adapter.py` `approve`. **Attacker input/path:** an agent invokes `tanuq propose`, then `tanuq approve --fingerprint …`, then `tanuq execute`. `cmd_approve` loads the environment and delegates without token, TTY, identity, or human-presence check; `approve` supplies `authorizer="human-operator"` to `ApprovalStore.grant`. **Authoritative failure:** the approval store receives a real, correctly bound grant, but nothing establishes its grantor was human. **Prerequisite:** agent capability to invoke local CLI commands; JSON-only submission is insufficient. **Reproducibility/impact:** source-backed command sequence should turn an otherwise approval-denied HIGH proposal into an approved execution, with durable approval evidence labeling the grant human. **Why missed:** binding/replay tests begin with a grant made by the test or assumed operator, and test the grant’s use rather than who can invoke the product grant endpoint. **Confidence:** high for the CLI boundary; deployment reachability is conditional on agent command permissions.

**CONFIRMED SECURITY GAP — arbitrary, ungoverned CLI export write.**  
**File/symbol:** `tanuq/cli.py` `cmd_export`. **Attacker input/path:** CLI `--out` → `out_path.parent.mkdir(...)` → `out_path.write_text(payload)`. **Authoritative failure:** no `PathPolicy`, configured-scope, risk, approval, or apply-journal decision governs that target; the payload is constrained to bundle JSON, but the destination is not constrained. **Prerequisite:** an initialized workspace and CLI invocation capability. **Reproducibility/impact:** an agent can overwrite an existing JSON settings file outside allowed paths; targeting the `.claude/settings.json` installed by `web._install_claude` replaces its hook configuration with a JSON evidence bundle. Whether an already-running vendor session reloads settings immediately is untested; the ungoverned overwrite itself is explicit in source. **Why missed:** research calls export a read-only *projection* and approval tests exercise patch apply, not `--out`. **Confidence:** high for arbitrary destination overwrite, conditional for subsequent vendor-hook behavior.

**CONFIRMED SECURITY GAP — CLI force-reset of authoritative scope.**  
**Files/symbols:** `tanuq/cli.py` `cmd_init`; `tanuq/config.py` `init_workspace`, `validate_config_values`, `save_config`; `tanuq/runtime.py` `load_environment`. **Attacker input/path:** `init --force --yes --workspace <initialized workspace>` with no `--allowed-path` → default whole-workspace scope → overwritten config → later runtime loads wider scope. **Authoritative failure:** validation checks containment within the workspace, not that the new scope is no wider than the old one; no human-authentication or governed proposal boundary protects this operator command. **Prerequisite:** an originally narrower configuration, CLI invocation capability, and a fresh environment load for subsequent execution. **Reproducibility/impact:** paths previously excluded but inside the workspace become eligible for governed proposals. **Why missed:** proposal-scope tests forge `patch.allowed_paths`; they do not exercise force re-registration. **Confidence:** high. This is not a claim that the user cannot intentionally reconfigure scope; it is a failure to distinguish that user from an agent allowed to call the CLI.

**CONFIRMED SECURITY GAP — pending content exposed without the web token to a local HTTP client.**  
**File/symbols:** `tanuq/web.py` `Handler.do_GET`, `_pending_view`. **Attacker input/path:** unauthenticated `GET /api/pending` → pending record → `old_preview` and `new_preview`, up to 2,000 characters each. `_check_token` runs for POST, not this GET. **Authoritative failure:** the token boundary protects mutations but not these potentially sensitive proposal contents. **Prerequisite:** a reachable running loopback UI and another principal’s pending proposal. **Reproducibility/impact:** local clients can read pending diff previews without knowing the device token; this does not grant execution authority. **Why missed:** secret-safety tests check ledger/event payloads, not the pending HTTP representation. **Confidence:** high for unauthenticated local disclosure. `Handler._headers` also accepts origins by `startswith("http://localhost")`/`startswith("http://127.0.0.1")`, which includes attacker-controlled suffix domains; whether a particular browser permits the resulting cross-origin loopback read is **NEEDS EXPERIMENT**, not established by that string check alone.

**NEEDS EXPERIMENT — product approval TTL.**  
**File/symbol:** `tanuq/agent_adapter.py` `approve`. The grant omits `expires_at` while its response promises `APPROVAL_TTL_SECONDS=3600`; tests establish expiry for explicit values, not this default. If the omitted value means no expiry, an old unconsumed approval can authorize later than the product tells the operator. **Prerequisite:** an unconsumed HIGH/CRITICAL grant. **Confidence:** high in the call-site omission; unresolved as a vulnerability until the store default or a real product grant record is checked.

**NEEDS EXPERIMENT — verifier-induced out-of-scope mutation.**  
**Files/symbols:** `tanuq/verification_profile.py` `related_test_candidates`/`select_test_targets`; `tanuq/agent_adapter.py` `execute`. A MEDIUM application-module change can be selected for verification by an existing related test that imports that changed module. The source does not treat imports as same-run test targets; TANUQ states it has no OS sandbox. An import-time side effect could write outside configured scope while verification passes, without a journal intent for that other path. **Prerequisites:** a selected importing test and payload classified below the approval gate. **Confidence:** material architectural concern, but the real verifier subprocess and this interleaving are not exercised in the supplied tests, so not labeled confirmed.

**HARDENING / NO GAP established:** instance-local coordinator reservations leave file-execution races to downstream checks; no supplied test demonstrates an approval double-spend. Direct `FileApplier.apply(..., scope=...)` without governance is explicitly demonstrated by `test_p3_no_direct_write_bypass_around_pipeline`, but is not reachable from proposal JSON merely because the primitive exists. Research E1/E3 semantic composition and E5 post-verification drift are established limits, not newly discovered approval-transfer exploits.

## 11. UNRESOLVED QUESTIONS

Does `ApprovalStore.grant` assign a one-hour expiry when `agent_adapter.approve` omits `expires_at`? Can a selected real pytest target execute imported, newly patched code with filesystem side effects outside scope? What synchronization, if any, do the unprinted apply primitives provide between final old-content/path checks and replacement? And, for each actual agent deployment, are CLI operator commands accessible to the model or is it confined to proposal JSON? These answers affect **which** confirmed CLI paths an agent can exercise; they do not change what the CLI source permits.

## 12. SINGLE MOST VALUABLE NEXT EXPERIMENT

In a disposable initialized workspace, submit a HIGH proposal through the real CLI, grant it with **`tanuq approve`**, and inspect that grant’s durable approval-ledger `created_at` and `expires_at` before executing anything. Check whether the recorded expiry is approximately 3,600 seconds after creation or is absent/non-expiring; if absent, test the store’s expiry decision at a controlled time beyond one hour against that same grant. This single experiment resolves whether the **actual product approval call**, rather than tests using explicit expiry arguments, enforces the TTL it promises.
